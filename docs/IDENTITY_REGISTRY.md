# Canonical Identity Registry — Implementation Notes

**Status:** canonical identity foundation and economic-supply/classification extension are merged in PRs #2 and #3. Effective-dated provider alias history is the next implementation increment.
**Governing source:** MVP_IMPLEMENTATION_BLUEPRINT.md and DATA_IDENTITY_AND_AGGREGATION.md.

## Scope delivered

The registry establishes distinct canonical records for underlyings, issuers, issuer products, networks, product deployments, venues, perpetual contracts, provider aliases, economic-supply groups/memberships and versioned classifications.

Each record receives an internal UUID. Provider IDs, symbols and native contract/market identifiers are attributes or aliases, never internal primary keys.

## Enforced identity rules

1. Issuer products are unique by issuer + native product ID. Different issuers can issue distinct products against the same underlying.
2. A deployment is unique by network + normalized contract/mint identifier. The same product can have multiple network deployments without multiplying its product identity.
3. EVM deployment identifiers must be 20-byte hexadecimal addresses and are lowercased for comparison.
4. Non-EVM identifiers are preserved byte-for-byte at the string level; Solana mint identifiers are case-sensitive.
5. Provider aliases target an existing canonical entity and are effective-dated. Reuse of the same provider + namespace + external ID is allowed only in non-overlapping periods.
6. Alias resolution is exact and supports an explicit `as_of` date. Symbol/name namespaces are aliases, not fuzzy identity keys.
7. Perpetual identity uses venue + domain + native market ID. Builder-scoped perpetuals require a domain; display symbols are not contract IDs.
8. Unknown canonical entity IDs return 404. No default BTC/NVDA fallback exists.
9. Unknown representation type remains explicit; the API does not infer bridge/wrapper status or legal rights.
10. Deployment verification is explicit and defaults to false.
11. Economic-supply membership is evidence-bearing and unverified by default; no bridge/wrapper equivalence is inferred.
12. Classification records are effective-dated and require source/evidence; provider-global inclusion remains nullable.

All routes are under /api/v1/registry:

| Underlyings | POST/GET /underlyings | Stable economic reference |
| Issuers | POST/GET /issuers | Issuer identity |

| Networks | POST/GET /networks | Canonical network namespace |
| Deployments | POST/GET /deployments | Product-specific chain representation |

| Provider aliases | POST/GET /aliases | Provider-native identity mapping |
| Alias resolver | GET /aliases/resolve | Exact provider + namespace + external ID; optional `as_of=YYYY-MM-DD` |

OpenAPI is generated by FastAPI at /docs.

## Effective-dated provider aliases

New alias records require `effective_from`; `effective_to` is optional and must be later than the start. Periods are half-open: the start is inclusive and the end is exclusive. The same provider + namespace + external ID cannot have overlapping periods, even if the proposed target differs.

Use `PATCH /aliases/{alias_id}/close` to set an alias end date once; the operation rejects a date at/before its start, repeated closure, and overlap with another alias. The resolver accepts `as_of=YYYY-MM-DD`. If omitted, it resolves against the API server's current date. Use provider namespaces such as `symbol` and `name` for exact symbol/name aliases. They remain provider-scoped hints and never trigger fuzzy matching.

Migration 0003 leaves the start date null for pre-existing alias rows because their historical start is unknown. These legacy rows remain resolvable until an explicit end date is recorded. A null historical start is not evidence that the alias was valid at any particular past date.

## Database and migration

SQLAlchemy 2.x models target PostgreSQL for shared environments. Alembic migrations 0001–0003 create the identity registry, economic-supply/classification records and effective-dated provider alias history. SQLite is used only for isolated automated tests and migration verification.

## Explicitly not delivered

- Perpetual contract migration history.
- Spot-market, pool and lending-market registry entities.
- Registry bulk import, reconciliation and unresolved-mapping workflow.
- Authentication/authorization and audit logging for registry mutations.
- Provider ingestion, source observations, market metrics or frontend integration.

The registry must not be exposed as a public write API until authentication, authorization, audit logging and operational controls are implemented.
