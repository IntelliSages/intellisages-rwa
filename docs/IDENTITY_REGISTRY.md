# Canonical Identity Registry — First Implementation Slice

**Status:** implemented on PR #2; frontend and backend CI passed, awaiting merge.  
**Governing source:** MVP_IMPLEMENTATION_BLUEPRINT.md and DATA_IDENTITY_AND_AGGREGATION.md.

## Scope delivered in this slice

The backend registry establishes distinct canonical records for:

- Underlying assets
- Issuers
- Issuer products
- Networks
- Product deployments
- Venues
- Perpetual contracts
- Provider aliases

Each record receives an internal UUID. Provider IDs, symbols and native contract/market identifiers are attributes or aliases, never internal primary keys.

## Enforced identity rules

1. Issuer products are unique by issuer + native product ID. Different issuers can issue distinct products against the same underlying.
2. A deployment is unique by network + normalized contract/mint identifier. The same product can have multiple network deployments without multiplying its product identity.
3. EVM deployment identifiers must be 20-byte hexadecimal addresses and are lowercased for comparison.
4. Non-EVM identifiers are preserved byte-for-byte at the string level; in particular, Solana mint identifiers are case-sensitive.
5. Provider aliases are unique by provider + namespace + external ID and must target an existing canonical entity.
6. Alias resolution is exact. Symbols are not fuzzy identity keys.
7. Perpetual identity uses venue + domain + native market ID. Builder-scoped perpetuals require a domain; display symbols are not contract IDs.
8. Unknown canonical entity IDs return 404. No default BTC/NVDA fallback exists.
9. Unknown representation type remains explicit; the API does not infer bridge/wrapper status or legal rights.
10. Deployment verification is explicit and defaults to false.

## API routes

All routes are under /api/v1/registry:

| Resource | Create/list | Notes |
|---|---|---|
| Underlyings | POST/GET /underlyings | Stable economic reference |
| Issuers | POST/GET /issuers | Issuer identity |
| Issuer products | POST/GET /products | Distinct issuer-native products |
| Networks | POST/GET /networks | Canonical network namespace |
| Deployments | POST/GET /deployments | Product-specific chain representation |
| Venues | POST/GET /venues | Venue/protocol identity |
| Perpetual contracts | POST/GET /perpetual-contracts | Exact venue/domain/native market |
| Provider aliases | POST/GET /aliases | Provider-native identity mapping |
| Alias resolver | GET /aliases/resolve | Exact provider + namespace + external ID |
| Canonical entity | GET /entities/{entity_type}/{entity_id} | Exact type + internal ID |

OpenAPI is generated by FastAPI at /docs.

## Database and migration

SQLAlchemy 2.x models target PostgreSQL for shared environments. Alembic migration 0001 creates the initial registry schema. SQLite is used only for isolated automated tests and migration verification.

## Explicitly not delivered yet

- Effective-dated alias history, symbol/name aliases and contract migration history.
- Economic-supply groups and evidence-backed bridge/wrapper equivalence.
- Versioned asset classification and provider-global inclusion evidence.
- Spot-market, pool and lending-market registry entities.
- Registry bulk import, review queue and unresolved-mapping workflow.
- Authentication/authorization for registry mutations.
- Provider ingestion, source observations, market metrics or frontend integration.

These remain open tasks. The registry must not be exposed as a public write API until authentication, authorization, audit logging and operational controls are implemented.
